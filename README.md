# 误报普查：9 个安全扫描器仓库的实测数据

> 一句话结论：**在 9 个真实安全工具仓库上，我的规则报了 33 条"疑似密钥"，逐条判定后 0 条是真泄露——33 条全部是它们自己的检测规则文件。**

## 为什么做这个普查

GitHub 上关于"密钥扫描误报"的真实 issue 很多（搜 `secret scanning false positive` 有 22 个仓库在提），
但**没有人给出误报到底占多少、都是什么类型**的实测数据。所以我扫了一批真实仓库，把数据摊开。

## 方法（可复现）

1. 选 9 个公开的安全/扫描类仓库（名单见 `scanned-repos.txt`），`git clone --depth 1`
2. 用 `review.mjs` 跑一遍（只读，本地，不上传任何代码）
3. 每条候选按 6 类语境分诊：测试夹具 / 扫描规则 / 文档模板 / 构建产物 / 检测器自身 / 知识库快照

## 结果

## 这个数据说明了什么

**扫描器互相扫对方，几乎必然"发现密钥"**——因为规则文件里写的就是"密钥长什么样"的正则。
这不是谁的错，是**缺少语境判定**的必然结果。

如果按误报率算：33/33 = **100% 误报**（在这批仓库上）。

## 这个数据**不**说明什么（重要）

1. 不说明这些仓库安全——它们把密钥放在别处，或者我覆盖的 6 类特征没命中；
2. 不说明这些工具差——它们扫的是**全 git 历史**，我只扫了工作树；
3. 不代表全行业误报率——这是 9 个**安全工具仓库**，本身是误报率最高的样本；
4. 样本极小（9 个仓库 / 240 文件），**不足以外推**。

## 复现

```bash
git clone --depth 1 https://github.com/tillson/git-hound.git
node review.mjs git-hound --json
# → 31 条候选，全部 triage=rulefile，critical=0
```

## 我在这次普查里修掉的自己的 bug

- 起初 `git-hound` 报 31 条"真高危"→ 分诊漏了 `rules/*.yml` 这类**签名规则文件** → 已补 `rules|signatures|patterns|detectors` 目录与 `*.regex(es)?|*.patterns?` 文件名识别
- 起初 `apkleaks` 报 2 条 → `config/regexes.json` 未识别 → 已补文件名规则

**这两个 bug 是普查捡出来的，不是我想出来的。**

## 这组数据推翻了我自己的卖点

第一批（安全工具仓库）33 条候选全来自规则文件；第二批（主流库）几乎**一条都没有**。
两组加起来说明一件我不想承认的事：

> **我的"0 误报"有一半是因为"我本来就扫不出东西"。**
> 6 类强特征太窄——泛型仓库里根本没有 `AKIA…`/`ghp_…` 这类字符串。

所以正确的产品定位不是"我来扫你的仓库"（我覆盖太薄），
而是**"你把现有扫描器的输出给我，我做语境分诊"**——我的价值在判定，不在发现。

这条修正来自数据，不是来自思考。

## 证据缺口（2026-11-24，一位读者审计后修）

一位读者逐文件核了这份普查的工件，提出三处，**都对**。逐条处置：

### 1. 复现命令引用的 `review.mjs` 不在仓库里（已修）

原来仓库只有 `README.md` 与 `scanned-repos.txt` 两个文件，而"复现"一节写着 `node review.mjs`。
**方法被描述了，却没有被交付** —— 那是"一个别人能检查的声明"和"一个别人能重复的声明"之间的差别。
`review.mjs` 现已随仓库发布，`node review.mjs --self-test` 可自证。

### 2. `scanned-repos.txt` 列 12 个仓库，正文说 9 个（如实记录，未编造原因）

名单 12 行，矩阵 9 行，缺行的三个是 `edoardottt/cariddi`、`Pantheon-Security/medusa`、
`MaxHu-xuan/chat-archive-guard`。

**我不知道它们为什么没进矩阵** —— 工件里没有记录。能从数字说的只有一件：`medusa` 那一行写着
37,066 文件，是已发布语料（2,242 文件）的 16 倍，若计入会改写每一个聚合值。所以"漏了三行"不是
排版疏漏，而是会影响结论的口径问题。**在补上真因之前，正文的"9 个"应按"9 个已计入"理解。**

### 3. 缺的那项测试不是召回率，是判定的另一侧（已补，并且它证伪了我）

读者的原话：33 条判定全是 `rulefile`，**一个对所有输入都回答 `rulefile` 的分类器能完美复现这张表**。
所以"33 → 0"检验的是语料，不是判定。

我照他说的做了四格植入测试，**结果两个方向都错**：

| 格 | 内容 | 修前 | 修后 |
|---|---|---|---|
A | 真格式密钥在 `src/` | critical ✓ | critical ✓ |
B | 假密钥在 `tests/` | fixture ✓ | fixture ✓ |
**C** | **真格式密钥在 `tests/`** | **fixture（被埋掉）** | **critical ✓** |
**D** | **占位符在 `src/`** | **critical（误报）** | **fixture ✓** |

根因：分诊**只看路径**——路径含 `tests/` 就归 fixture。于是一个真密钥只要放在测试目录下就会被
静默埋掉（假阴性，危险方向），而 `sk-test-1111…` 这种明显占位符放在 `src/` 下会被报成高危（假阳性）。

修法：**值先判，路径只作提示**。占位符按值识别（长度、重复字符、常见假值标记、字符类多样性）；
路径说 fixture 但值看起来是真的 ⇒ **不许埋，按 real 上报**。

`--self-test` 现在是这四格，并且**能被注入打红**：把判定退回纯路径版，C 格立刻变红（3/4, rc=1）。

### 结论怎么改

原文的"28 条告警 → 0 真泄露"这句话，在判定未证明会开火之前，**只支撑"这些命中都在规则文件里"，
不支撑"不是你的泄露"**。补上 C 格之后，"真"这个方向第一次有了一件可复现的证据。
